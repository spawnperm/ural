# Соглашения о вкладе

## Ветки и коммиты

- Ветки от `main`, имя по смыслу: `fix/env-docs-gate`, `feat/version-compare`.
- Сообщения в стиле Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`,
  `refactor:`, `chore:`. Тема до 200 символов, на русском или английском —
  главное, одинаково внутри одного PR.

## Перед PR

Запустите локально всё, что проверяет CI:

```bash
pnpm run lint
pnpm test
pnpm run check:env-docs
pnpm run build
```

Если добавили переменную окружения — допишите её в `.env.example` с
комментарием, в каком файле она читается. `check:env-docs` не пропустит PR без
этого.

## Требования к коду

- **TypeScript strict.** `any` допустим только на границе с данными, форма
  которых действительно неизвестна (ответ внешнего API), и рядом должен быть
  комментарий, почему тип неизвестен.
- **Серверные модули без побочных эффектов при импорте.** `listen` и чтение
  окружения — только в `server.ts` и `config.ts`. Из-за этого тесты могут
  импортировать фабрику приложения, не поднимая сервер.
- **Ошибки — через `sendProblem`.** Полу-JSON, полу-текст ломает типизированные
  клиенты; один формат (RFC 7807) для всех ошибок.
- **Внешние процессы — только `execFile` с вектором аргументов.** Никакого
  `exec`, `spawn` с `shell: true` и склейки строк в команду.
- **Новые зависимости — с обоснованием в PR.** Для одной функции лучше
  написать двадцать строк, чем тянуть пакет: каждый пакет это обновления, CVE и
  вес бандла.

## Тесты

Тесты — часть изменения, а не отдельная задача. Минимум:

- новая ветка валидации → тест на отказ и на успех;
- новый маршрут → контрактный тест (статус, `content-type`, форма тела);
- правка `gitService` → интеграционный тест на реальном временном репозитории,
  а не на моке.

Подробнее — [`docs/TESTING.md`](docs/TESTING.md).

## Стиль общения в коде

Комментарии объясняют **почему**, а не что. Если строка кажется странной,
комментарий должен снять вопрос «зачем так», иначе его стоит удалить.

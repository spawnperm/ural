# Model: контекст «Приглашения»

DDD в этом проекте применён **точечно**: только там, где есть настоящая предметная
область с правилами, которые дорого нарушить. Не «папки на каждую букву DDD», а
одна модель, которая устранила конкретный дефект.

## 1. Почему только один контекст

| Контекст из документации | Есть ли в коде | Что сделано |
|---|---|---|
| Приглашения (QR, визиты) | да — логика в симуляторе | **модель реализована** |
| Прохождение (попытки, ответы) | частично — вопросы в компоненте | нет: правил почти нет, вопросы — контент |
| Достижения (печати, серии) | да — в Temporal-саге | описано типами, не агрегатами |
| Контент, Аутентификация | нет | нечего моделировать |

Агрегаты Прохождения и Достижений появятся, когда появится их поведение. Создавать
их «на будущее» — та самая ошибка, от которой DDD защищает.

## 2. Что было не так без модели

Симулятор хранил приглашение как обычный интерфейс:

```ts
interface InvitationRecord {
  expiresAt: string;   // когда истекает
  expired: boolean;    // ...и флаг, истекло ли
}
```

**Два источника правды для одного факта.** Их можно было рассинхронизировать, и они
были: сценарий «Уже погашено» нёс `expired: false` при `expiresAt` в прошлом —
флаг говорил «всё хорошо», дата говорила «истекло», а UI верил флагу.

Проверка дефекта:

```js
record = { expiresAt: '2026-09-25T18:00:00Z', expired: false }
Date.parse(record.expiresAt) < Date.parse('2026-11-20')  // true
record.expired                                           // false
// ПРОТИВОРЕЧИЕ
```

## 3. Как это исправлено

`expired` больше **не поле**. Истечение вычисляется:

```ts
invitation.isExpiredAt(now)   // !expiresAt.isAfter(now)
```

Противоречие нельзя даже выразить — нечего рассинхронизировать.

## 4. Структура

```
src/domain/invitations/
  valueObjects.ts   InvitationToken, SealCount, Instant, DomainError
  events.ts         InvitationIssued, InvitationRedeemed, InvitationRedeemRejected
  Invitation.ts     агрегат: инварианты, состояния, события
src/data/
  redemptionWorkflow.ts   поток как данные: правила + генерация диаграммы
```

### Value objects

Не «для красоты» — каждый убирает класс ошибок:

| Объект | Что делает невозможным |
|---|---|
| `InvitationToken` | пустой токен, произвольную строку, потерю регистра |
| `SealCount` | отрицательное и дробное количество печатей |
| `Instant` | сравнение дат как строк, забытый часовой пояс |

`Instant` нормализует `+05:00` в `Z` при разборе: `'2026-11-20T16:45+05:00' <
'2026-11-20T11:45Z'` ложно как строки и верно как моменты времени. Старый код
сравнивал строки и не замечал этого.

### Агрегат

Инварианты, которые проверяются в одном месте и больше нигде:

1. Погашенное приглашение нельзя погасить повторно.
2. Истёкшее нельзя погасить.
3. `expiresAt` позже момента выдачи.
4. Email участника содержит `@`.
5. Истечение — функция от `expiresAt`, а не хранимое поле.

Фабрики `issue()` и `restore()` разделены осознанно: загрузка уже погашенного
приглашения не должна заново порождать событие `InvitationIssued`, иначе
обновление страницы переиграло бы историю.

### События

`InvitationIssued`, `InvitationRedeemed`, `InvitationRedeemRejected` — это ровно те
события, которые документация (`BOUNDED_CONTEXTS`) приписывает контексту.
Агрегат копит их в буфере, а не публикует сам: он не должен знать про NATS,
Temporal или React. Прикладной слой решает, что с ними делать.

## 5. Границы и что сознательно не сделано

- **Нет репозитория.** Состояние живёт в `useState` компонента. Репозиторий нужен,
  когда появится хранилище; сейчас он был бы интерфейсом без реализации.
- **Нет прикладного слоя.** Обработчик компонента выполняет его роль: вызвать
  агрегат, сохранить снапшот, показать код. На четырёх операциях отдельный слой
  был бы церемонией.
- **Нет антикоррупционного слоя.** Нет второго контекста, с которым надо
  договариваться.
- **Сущности `Visit` нет.** Визит пока представлен событием `InvitationRedeemed`.
  Отдельный агрегат появится, когда у визита будет собственное поведение
  (продление, отмена, перенос).

## 6. Как проверено

`src/tests/invitationAggregate.test.ts` и `redemptionWorkflow.test.ts` — 193 теста
всего набора:

- инварианты агрегата: двойное погашение, истечение на границе, порядок отказов;
- value objects: формат токена, отрицательные печати, нормализация времени;
- **выводимость**: снапшот не содержит поля `expired`, а состояние выводится только
  из `expiresAt`;
- `restore()` не переигрывает историю;
- поток и агрегат не расходятся в решении об отказе.

Тесты нашли два противоречия в модели — `notFound` был одновременно терминальным и
имел правило, а `success` не имел правила вовсе — и один несогласованный
демо-сценарий. Все три исправлены в данных, а не в ожиданиях тестов.

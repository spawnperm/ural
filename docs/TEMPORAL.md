# Temporal: оркестрация саг квеста

Документ объясняет, **что** здесь реализовано через Temporal, **почему** именно
это и — что важнее — почему Temporal не используется в самом портале.

## 1. Почему Temporal здесь, а не в сервере портала

Портал документации — это React-приложение и три HTTP-эндпоинта. Единственная
асинхронная операция в нём — `git push`, которая длится секунды и ограничена
rate-limit'ом. Durable execution для неё был бы молотком для мухи: Temporal
требует собственного сервера, базы и воркера, а у портала нет даже БД — его
состояние это файлы и git.

Temporal нужен **системе квеста**, которую портал документирует. В
[`src/data/projectDocs.ts`](../src/data/projectDocs.ts) он описан так:

> «ведёт 3-месячную серию печатей, ставит отложенные таймеры протухания
> приглашений (`expires_at`) и гарантирует идемпотентные ретраи генерации QR/PDF»

Это три конкретных сценария, и они реализованы в `src/temporal/` как эталонная
реализация. Эксплуатация — задача сервиса `workers`, а не портала.

## 2. Три workflow

### `sealSeriesWorkflow` — серия печатей

Самая содержательная сага. Участник проходит квест по историческим дорогам: у
каждого этапа есть маркер с QR, который нужно отсканировать в своё окно.

```
этап открылся ──> ждём сигнал ИЛИ конец окна ──> печать записана?
                                                  ├─ да → следующий этап
                                                  └─ нет → серия провалена
```

Почему это Temporal, а не cron:

- **Время.** Серия живёт месяцами. Workflow переживает перезапуски воркера и
  деплои: его состояние — это история событий, а не переменные в памяти.
- **Таймеры.** `sleep()` на недели — штатная операция. Периодический обход всех
  приглашений вместо этого читал бы строки, которые ещё не наступили.
- **Сигналы.** Участник сканирует маркер — workflow просыпается немедленно через
  `condition()`, а не по расписанию.

Промежуточный дизайн (первая версия) ждал окно этапа **после** успешной печати.
Смоук-тест на реальном сервере это поймал: workflow висел 10 дней, хотя участник
уже всё отсканировал. Ожидание перенесено в ветку «печать не состоялась».

### `invitationExpiryWorkflow` — протухание приглашения

Таймер, а не cron: workflow стартует при выдаче приглашения и спит до
`expires_at`. Это дёшево (спящий workflow не занимает ресурсов) и не дрейфует,
когда планировщик остановлен на время деплоя.

### `generateCredentialsWorkflow` — QR и PDF

Ценность — в идемпотентности. `outputKey` детерминирован для попытки, поэтому
ретрай перезаписывает тот же артефакт, а не создаёт второй. Именно это делает
bounded retries безопасными.

## 3. Правила, на которых держится корректность

Код workflow должен быть **детерминированным**: при replay после падения воркера
Temporal прогоняет его заново по истории событий и сравнивает результат. Поэтому
в `workflows.ts`:

| Разрешено | Запрещено |
|---|---|
| `Date.now()`, `new Date()` — привязаны к Workflow Task time | `Math.random()` — используйте `uuid4()` из SDK |
| `sleep()` | реальные таймеры, `setTimeout` |
| activities для любых эффектов | `fetch`, `node:fs`, `node:crypto` напрямую |
| `condition()` | опрос внешнего состояния циклом |

Нарушение компилируется и падает при replay в проде — в худший момент. Поэтому
`workflows.ts` импортирует только `@temporalio/workflow`, а activities лежат в
отдельном модуле: SDK сам собирает workflow-бандл и не пропустит лишние импорты.

## 4. Идемпотентность

Temporal доставляет activities **как минимум один раз**, поэтому каждая из них
обязана быть идемпотентной. Это не пожелание, а условие корректности:

- `recordSeal` — вставка по ключу `(attemptId, stageId)`; повтор возвращает
  `created: false`;
- `expireInvitation` — ключ по токену; повторное протухание не ошибка;
- `renderCredentials` — детерминированный `outputKey`; повтор перезаписывает.

Тесты в `src/tests/temporalActivities.test.ts` вызывают каждую activity дважды и
проверяют, что второй вызов ничего не изменил.

## 5. Как проверить

```bash
# 1. Сервер (dev, SQLite, порт 7233 и Web UI на 8233)
pnpm run temporal:up

# 2. Воркер — в отдельном терминале
pnpm run temporal:worker

# 3. Сквозная проверка на живом сервере
pnpm run temporal:smoke
```

`temporal:smoke` запускает реальные workflow и читает результаты через клиент:
генерацию артефактов, идемпотентность повторного старта, таймер протухания и
серию печатей. Моки SDK проверили бы только то, что код компилируется; этот
скрипт проверяет, что песочница принимает workflow и контракты activities
сходятся.

Web UI: <http://localhost:8233> — история событий, таймеры, входы/выходы.

## 6. Ограничения этой реализации

Честно о том, чего здесь нет:

- **Хранилище в памяти.** `createInMemoryStore` — интерфейс, а не персистентность.
  Реальная эксплуатация подменяет его на PostgreSQL за тем же интерфейсом
  `QuestStore`; workflow при этом не меняются.
- **Публикатор пишет в лог.** События должны уходить в NATS JetStream
  (`pstu.events.QuestContext.*`), но подключение брокера — решение развёртывания.
  `createConsolePublisher` и `createCapturingPublisher` имеют одну сигнатуру с
  будущим NATS-публикатором.
- **Рендер — дайджест, не PDF.** `createDigestRenderer` даёт детерминированный
  SHA-256 вместо реального PDF/QR-пайплайна. Свойство, которое проверяется, —
  детерминированность ключа, а не качество вёрстки.
- **Dev-сервер без аутентификации.** `docker-compose.temporal.yml` публикует
  порты только на loopback. Боевое развёртывание требует mTLS, отдельной
  БД и ролей.
- **Нет версионирования workflow.** При изменении логики запущенные серии
  продолжат выполняться по старым путям. Перед боевым запуском нужен
  `workflow.patched()` или отдельная очередь задач.
